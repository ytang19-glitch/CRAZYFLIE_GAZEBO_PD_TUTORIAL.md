# Crazyflie ROS 2 Debugging Guide

Use this guide to check whether the ROS 2 nodes, topics, odometry, and controller force are working in the Crazyflie Gazebo PD demo.

> Run these commands **inside the running Docker container**. Keep the simulation running in another terminal.

## 1. Open a debugging terminal

From PowerShell, Windows Terminal, WSL, or an Ubuntu terminal, enter the container:

```bash
docker exec -it crazyflie_pd_demo bash
```

Then load the ROS 2 workspace:

```bash
source /opt/ros/jazzy/setup.bash
source /workspace/install/setup.bash
```

If the second command reports that the file does not exist, build the workspace first or confirm that the demo was started successfully.

## 2. Check the running ROS 2 nodes

```bash
ros2 node list
```

Expected nodes normally include:

```text
/trajectory_node
/pd_controller
```

You may also see Gazebo bridge, robot-state-publisher, or other simulation nodes.

### If a node is missing

- If `/trajectory_node` is missing, the reference path is not being published.
- If `/pd_controller` is missing, no PD control force is being calculated.
- Check the simulation terminal for Python errors, missing packages, or a node that exited.

For more information about a node:

```bash
ros2 node info /trajectory_node
ros2 node info /pd_controller
```

## 3. Check the available ROS 2 topics

```bash
ros2 topic list
```

Important topics for this demo are:

| Topic | Purpose |
| --- | --- |
| `/cf/reference` | Desired position and velocity generated by the trajectory node |
| `/cf/odom` | Actual Crazyflie position and velocity from Gazebo |
| `/cf/wrench` | Force command calculated by the PD controller |

If one is missing, use `ros2 node info` to determine which publisher or subscriber is absent.

## 4. Check the drone position

```bash
ros2 topic echo /cf/odom --field pose.pose.position
```

Typical output:

```yaml
x: 0.49
y: 0.06
z: 1.00
---
```

The values should update continuously while the drone moves.

### How to interpret the result

- Changing `x` and `y`: the drone is moving along the trajectory.
- `z` close to `1.0`: the drone is flying near the expected height.
- `z` close to `0.0`: the drone may be on or below the ground.
- No output: `/cf/odom` exists but no messages are arriving.
- Frozen values: Gazebo may be paused, or the odometry bridge/plugin may have stopped.

Press `Ctrl+C` to stop displaying messages.

Useful follow-up checks:

```bash
ros2 topic info /cf/odom -v
ros2 topic hz /cf/odom
```

`topic info` shows the publishers and subscribers. `topic hz` shows the message frequency.

## 5. Check the controller force

```bash
ros2 topic echo /cf/wrench --once
```

This prints one force command and then exits. The `force.z` value should usually be positive because the controller must counter gravity.

Example:

```yaml
entity:
  name: crazyflie
  type: 2
wrench:
  force:
    x: 0.01
    y: -0.02
    z: 0.45
```

For a drone mass of approximately `0.038 kg`, its weight is:

```text
mass × gravity = 0.038 × 9.81 ≈ 0.373 N
```

The vertical command does not need to equal `0.373 N` at every moment. It may be higher or lower while correcting altitude and vertical velocity.

### If no wrench message appears

Check whether the topic has a publisher:

```bash
ros2 topic info /cf/wrench -v
```

Then verify that both controller inputs are active:

```bash
ros2 topic hz /cf/reference
ros2 topic hz /cf/odom
```

The PD controller normally needs both the reference and the odometry before it can calculate a useful command.

## 6. Compare Ubuntu and WSL message frequencies

If the drone flies correctly on native Ubuntu but drops in WSL/Docker, compare the actual ROS 2 topic frequencies on both systems.

Check the controller output frequency:

```bash
ros2 topic hz /cf/wrench
```

If it is close to 1000 Hz, the output should look similar to:

```text
average rate: 998.5
    min: 0.0008s max: 0.0013s std dev: 0.0001s
```

This means `/cf/wrench` is publishing approximately 1000 messages per second.

Also check the two inputs used by the controller:

```bash
ros2 topic hz /cf/odom
ros2 topic hz /cf/reference
```

Record the results on native Ubuntu and WSL:

| Topic | Native Ubuntu | WSL/Docker | What it represents |
| --- | ---: | ---: | --- |
| `/cf/wrench` | _____ Hz | _____ Hz | Controller force-command publication |
| `/cf/odom` | _____ Hz | _____ Hz | New drone-state measurements |
| `/cf/reference` | _____ Hz | _____ Hz | New desired trajectory states |

> A high `/cf/wrench` frequency alone does not prove that the controller is receiving fresh information. For example, the controller may publish a force at 1000 Hz while `/cf/odom` and `/cf/reference` update at only 47 Hz. In that case, many wrench messages repeat a command calculated from an older state.

### Why WSL can behave differently

Native Ubuntu usually gives Gazebo and ROS 2 more direct access to CPU scheduling and graphics. WSL adds Windows, Docker, and virtualization layers. Under heavy load, this may cause:

- slower Gazebo simulation;
- irregular odometry timing;
- larger scheduling jitter;
- delays through the ROS–Gazebo bridge;
- repeated controller commands based on old odometry.

Check the simulation speed as well as the ROS message rates. In Gazebo, the **real-time factor** should remain reasonably close to `1.0`. If it falls far below `1.0`, simulated time is advancing more slowly than real time.

If the messages contain valid timestamps, delay can also be inspected with:

```bash
ros2 topic delay /cf/odom
ros2 topic delay /cf/wrench
```

If `ros2 topic delay` reports a timestamp problem, rely on `ros2 topic hz`, the Gazebo real-time factor, and the terminal logs instead.

## 7. Quick diagnosis table

| Observation | Likely cause | Next action |
| --- | --- | --- |
| `/trajectory_node` is missing | Trajectory node failed or was not launched | Read the simulation log and restart the launch file |
| `/pd_controller` is missing | Controller failed or was not launched | Check Python errors and controller parameters |
| `/cf/odom` is missing | Gazebo odometry or ROS–Gazebo bridge is not active | Check the odometry plugin and bridge configuration |
| `/cf/odom` exists but prints nothing | Topic has no active publisher | Run `ros2 topic info /cf/odom -v` |
| Position never changes | Gazebo is paused or force is not applied | Check Gazebo and inspect `/cf/wrench` |
| `z` quickly falls toward zero | Insufficient upward force or control instability | Check `kp`, `kd`, mass, acceleration limit, and `force.z` |
| `/cf/wrench` has messages but the drone does not respond | Wrong Gazebo entity name/type or bridge problem | Confirm entity name `crazyflie` and type `MODEL` |
| Figure-eight causes a fall | Aggressive reference or controller saturation | Return to safe gains and circle mode, then tune gradually |

## 8. Recommended debugging order

Run the checks in this order:

```bash
ros2 node list
ros2 topic list
ros2 topic echo /cf/odom --field pose.pose.position
ros2 topic echo /cf/wrench --once
ros2 topic hz /cf/wrench
ros2 topic hz /cf/odom
ros2 topic hz /cf/reference
```

The logic is:

1. Confirm that the programs are running.
2. Confirm that the communication channels exist.
3. Confirm that Gazebo is publishing the actual drone state.
4. Confirm that the controller is producing a force command.

## 9. Copy-and-paste debug report

When asking an instructor or opening a GitHub issue, include the output of:

```bash
ros2 node list
ros2 topic list
ros2 topic info /cf/odom -v
ros2 topic info /cf/wrench -v
ros2 topic hz /cf/odom
ros2 topic hz /cf/reference
ros2 topic hz /cf/wrench
ros2 topic echo /cf/odom --field pose.pose.position --once
ros2 topic echo /cf/wrench --once
```

Also include:

- the current `kp` and `kd` values;
- the selected trajectory (`circle` or `figure8`);
- whether Gazebo is paused;
- the relevant error messages from the simulation terminal;
- a screenshot if the drone is on the ground or behaving unexpectedly.
